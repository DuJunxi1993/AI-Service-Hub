# AGENTS.md — AI Service Hub

## What this is
Native macOS SwiftUI control panel (SwiftPM, macOS 26+, Swift 6.2) for a set of
local services. It is **not** a generic process supervisor: a service is either
**observed** (read-only) or **managed** (this app starts/stops it).

Branch: `macos`. This repo is an umbrella — `main` and `windows-wsl` exist for
other platforms; do not push macOS-only changes elsewhere.

## Build / run

| Goal | Command |
|------|---------|
| Produce signed `AiServiceHub.app` | `bash build.sh` |
| Build only (no bundle) | `swift build -c release` |
| Dev run | `bash run.sh` |
| Unit tests | `swift test` |
| Override config | `CONFIG=debug bash build.sh` (default: release) |

- **A full Xcode is required.** CommandLineTools lacks the SwiftUI macro plugin
  (`libSwiftUIMacros.dylib`), so `swift build` fails with "external macro
  implementation type 'SwiftUIMacros.StateMacro' could not be found".
  `scripts/xcode-env.sh` picks one (explicit `DEVELOPER_DIR` → `xcode-select`
  → `/Applications/Xcode.app` → `/Applications/Xcode*.app`).
- Bundle: `AiServiceHub.app` at repo root (regenerated by `build.sh`).
  Binary: `.build/<config>/AiServiceHub`.
- `swift test` exists and is expected to stay green. Do not add other test
  frameworks, SwiftLint or SwiftFormat.
- No third-party SPM dependencies.

## Layout

### `Sources/AiServiceHubCore/` — pure logic, **must not import SwiftUI**
- `Model/` — `LifecycleMode` (`.observed` / `.managed`), `ManagedDriver`
  (`.process` / `.container`), `ServiceDescriptor`, `ManagedSpec`
  (`ProcessSpec` / `ContainerSpec`), `Probe`, `ProbeResult`, `ServiceStatus`,
  `ServiceSnapshot`, `LogModels`.
- `Runtime/` — `CommandRunner` (async exec, concurrent stdout/stderr, timeout),
  `ProcessInspector` (`ps -A` enumeration, `lsof` ports, `sysctl` start time),
  `ExecutableLocator`, `DaemonSpawner` (`posix_spawn`), `DockerCLI`.
- `Services/` — `ProcessDriver`, `ProbeEvaluator`, `OwnershipLedger`.
- `Presets/` — `AstrBotPreset`, `HermesPreset`, `DSHPreset`.
- `Logs/` — `LogHub` (actor, per-source ring buffer + `AsyncStream`),
  `LogTailer` (file / glob / subprocess), `LineParser`.
- `Config/` — `AppConfig`, `ConfigStore` (JSON + `.bak`), `LegacyMigration`.
- `Support/` — `AppLog`, `PathExpander`, `ShellArgumentParser`,
  `ComposePortParser`, `WebUIURLDetector`.

### `Sources/AiServiceHub/` — SwiftUI app
- `App/` — `@main`, `AppDelegate`, scene commands.
- `State/` — `AppModel` (coordinator: refresh, start/stop, auto-start),
  `AppSettings` (config façade, `@Published` mirrors + JSON persistence).
- `Views/` — `MainWindow/`, `Settings/`, `Components/`, `MenuBar/`.
- `Utilities/` — `Theme`, `NotificationNames`.

## Non-obvious constraints

- **macOS app icons do not adapt to appearance.** The bundle icon (Finder,
  not-running Dock) is a single static `.icns`. Marking an appiconset with
  `appearances: luminosity/dark` is a **no-op on macOS** — actool silently
  drops the dark rendition and `Assets.car` keeps only "Any". (iOS 18 has
  this; macOS does not.) The `iconutil` `_dark` suffix convention is ignored
  by macOS too. The only appearance-aware app icon on macOS is the
  **running** Dock tile: `NSApp.applicationIconImage`, settable at runtime.
  So the bundle ships two `.icns` and `AppIconController` swaps
  `applicationIconImage` on appearance change.
- **The Dock icon follows the *system* appearance, not the in-app theme
  picker.** The in-app theme (跟随系统/浅色/深色) forces the *window*
  appearance, so `NSApp.effectiveAppearance` no longer reflects the system.
  Read the system state from the global `AppleInterfaceStyle` domain key
  instead (`SystemAppearance.isDark`). Note that any `UserDefaults` read
  falls back to the global domain — a custom suite cannot isolate it.
- **Never use `pgrep` to find processes.** On macOS 27 it misses processes
  spawned by GUI apps (verified: `pgrep -f "dsh web"` returns nothing while
  `ps -A` shows it). Use `ProcessInspector.snapshot()` and match in memory.
  Enumerate once per refresh; `ps` output for this machine is ~800 lines.
- **`CommandRunner` completion is driven by process exit**, not by pipe EOF
  events. The handlers must capture `self` strongly (plus `withExtendedLifetime`
  around the await) and `teardown()` must clear them — the first version used
  `[weak self]` and never resumed, hanging every test.
- **PID identity is `pid + p_starttime`** (`sysctl KERN_PROC_PID`), never pid
  alone — macOS recycles PIDs and killing the wrong process is unrecoverable.
- **Liquid Glass calls are macOS 26 only** (`glassEffect`, `glassProminent`).
  Keep them in the view layer; `AiServiceHubCore` must stay UI-free.
- **Package the zip with `ditto -c -k --keepParent --norsrc --noextattr`.**
  Without `--norsrc --noextattr`, `ditto` stores extended attributes as
  AppleDouble `._*` sidecars inside the zip. Those extra files land in
  code-signature-sealed directories, so an extracted copy fails
  `codesign --verify` with *"a sealed resource is missing or invalid"*.
  The CI workflow verifies this explicitly after packaging. (`COPYFILE_DISABLE=1`
  does **not** help — it still emits the `._` files.)
- **No customizable toolbar.** `MainWindowView` uses a plain `.toolbar { }` with
  fixed items. Do **not** add `.toolbar(id:)` or `customizationBehavior()` — it
  crashes on macOS 26.5.1. `AiServiceHubApp.init()` scrubs stale
  `NSNavToolbarCustomization-*` / `NSToolbar Identifier *` keys; keep that.
- **Never restore `.windowStyle(.hiddenTitleBar)`.** With it, SwiftUI renders the
  toolbar as a content-hugging floating capsule and **ignores**
  `ToolbarItem(placement:)` — every button ends up crammed at the left, and a
  `Spacer()` inside the item collapses to zero. The real title bar makes
  `.primaryAction` land on the window's trailing edge, which is what the toolbar
  buttons need. The `.toolbar` modifier must also be attached to the **detail**
  closure, not to `NavigationSplitView` — on the split view it lands in the
  sidebar column's toolbar region.
- **Do not combine `POSIX_SPAWN_SETSID` with `POSIX_SPAWN_SETPGROUP`** — it
  returns `EPERM` on macOS. `DaemonSpawner` uses SETSID only when `detached`.
- **Observed services must never be started/stopped.** `AppModel.start/stop`
  rejects them and the UI renders no buttons; keep both guards.
- **Config is the single source of truth** at
  `~/Library/Application Support/AI Service Hub/config.json`. Bump
  `AppConfig.currentSchemaVersion` when the shape changes and decode new fields
  with `decodeIfPresent` so older files keep loading.
- **Legacy migration reads the old bundle id explicitly**
  (`LegacyMigration.legacyBundleID = "com.djx.astrbotlauncher"`); the app's own
  `UserDefaults.standard` points at a different domain and is essentially empty.
- `.gitignore` excludes but may be present in the working tree:
  `AiServiceHub.app/`, `data/`, `*.dmg`, `*.zip`, `release-checksums.txt`.
  Don't commit them.

## CI

- `.github/workflows/build-macos.yml` runs on `macos-26` (GA, arm64, has the
  macOS 26 SDK). It runs `swift test`, `bash build.sh`, packages zip + dmg,
  and on `macos-v*` tags creates a GitHub Release.
- Release tags use `macos-v<semver>`.

## Releases

- `RELEASE.md` is the single source of truth. When cutting a release:
  1. Update the top "Latest Release" block — version, date, download table, SHA256.
  2. Prepend a new section to "Changelog" (reverse chronological).
  3. Bump `CFBundleShortVersionString` in `Resources/Info.plist`.
- The in-app version string is read from `Bundle.main`, not hardcoded.
- `LSMinimumSystemVersion` is fixed at `26.0`.

## Tests worth knowing

- `LiveProbeTests` asserts against the **real** `~/.hermes/gateway_state.json`
  and the live `dsh web` process, and skips when they are absent. Useful for
  verifying monitoring end-to-end on a real machine.
- `LegacyMigrationTests` injects a throwaway `UserDefaults` suite; it also
  asserts migration never writes back into the legacy domain.

## First-run notes

- Ad-hoc signing only. First launch triggers Gatekeeper; right-click the `.app`
  → Open, or `xattr -dr com.apple.quarantine AiServiceHub.app`.
- Upgrading from the old app: delete `/Applications/AstrbotLauncher.app`, then
  re-enable the login item in the new app's settings.
